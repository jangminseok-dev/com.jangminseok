## [01] 맡은 범위와 작업 방식

팀 역할 정본에서 장민석은 AI Evaluation Engineer로, "이 자리에 어떤 모델을 쓸 것인가"에 숫자를 붙이는 역할을 맡았습니다. 평가 러너(backend/scripts의 run_* 스크립트), 모델 평가 정본 문서, 실측 적립 파일(metrics.yml), Core 선정과 NPC 모델 선정 실험, provider 어댑터, 배포 지표(지연 p50/p95, GPU 상주량)가 이 범위입니다. 발표에서도 모델 평가 구간과 "숫자, 게이트, 모델 선정" 질문을 맡기로 정해져 있었습니다. 다만 역할 문서 스스로 인원이 적어 영역 구분 없이 교차 작업했다고 적고 있고, 팀원 전원이 온프레미스 서버 한 대에 SSH로 접속해 같은 계정으로 커밋했기 때문에 커밋 작성자로는 개인 기여를 가를 수 없습니다. 게임 엔진의 채점 코드 수정과 연구 사이트 운영처럼 역할표 밖에 걸친 작업은 아래에서 따로 표시했습니다.

## [02] 합격선을 먼저 정한 이유와 판정 순서

Core(계획, 관리, 채점)를 먼저 확정하고 NPC를 나중에 정한 이유는 실패 비용이 비대칭이었기 때문입니다. Core가 틀리면 세계가 굴러가지 않고 채점이 무너지지만, NPC가 어색한 것은 게임이 돌아가는 채로 고칠 수 있습니다. 실제로 초기에 Core의 질문 답변 역할이 폴백으로 무너진 사례가 있었습니다. 게이트는 스키마 준수율, 폴백률, 극성 쌍(같은 사건을 반대로 묻는 두 문항이 모두 맞아야 통과), 상주량, 지연으로 구성했습니다. 지연을 품질과 별개 축이 아니라 탈락 기준으로 둔 이유는 밤 질문과 밤 채점이 플레이어가 멈춰서 기다리는 자리였기 때문입니다. 지연 값은 단발 측정이 아니라 문항 전체의 p95로 판정했습니다. 재생성이 붙으면 시간이 곱절로 늘어나기 때문입니다. 후보를 한 번에 다 돌리지 않고 프로토콜 호환, 스모크, 본실험(n=3), 동시 상주, 루프 완주의 다섯 단계로 걸렀습니다. 채택은 마지막 루프 완주 단계를 통과한 뒤에만 했습니다. 단일 종합 점수는 가중치가 임의라는 이유로 만들지 않았습니다. 지연 기준값(질문 답변 p95 5초 등)은 통념으로 잡은 값이고 플레이테스트로 검증한 값은 아니라고 문서에 밝혀 두었습니다.

## [02] 동시 상주를 잰 방법과 한계

GPU는 RTX 5060 Ti 16GB 한 장이었습니다. 처음에는 모델 파일 크기로 예산을 추정했지만, 한 후보는 디스크 8.95 GiB인데 실제 상주가 3.06 GiB로 크게 어긋나 이후 예산 판정은 실측 상주량으로만 했습니다. 동시 상주 측정은 NPC 모델을 먼저 올려 운영 상태를 재현하고, Core 후보를 올린 뒤 NPC 호출과 Core 호출을 세 라운드 번갈아 보내면서 매 호출 직후 상주 목록을 찍어 축출과 CPU 오프로드를 확인하는 방식입니다. 채택 후보 조합은 모델 합계 12.34 GiB, 장치 실측 최고 13,326 / 16,311 MiB(81.7%)에서 축출 0이었습니다. 두 값은 서로 다른 계측(모델별 상주량 합과 장치 전체 사용량)입니다. 한계도 분명합니다. 한 라운드에 약 1분인 단시간 측정이고, 동시 사용자 부하 시험은 하지 않았습니다(측정 전). NPC 41문답 실패 0, 중간값 2.599초는 9월 15일 Gemma를 NPC로 쓴 별도 검사이며, 메모리 저장소를 쓴 유스케이스 시간이라 실제 API와 DB 지연은 빠져 있습니다.

## [03] 채점 점수가 오른 이유와 임베딩을 되살린 자리

플레이테스트 8판에서 정답에 도달해도 점수가 21~42%에 머물렀습니다. 골든 세트 3종(정답형, 절반형, 오답형)을 오프라인으로 채점하는 캘리브레이션 러너를 만들어 원인을 좁혔고, 유사도 상위 3개만 심판에게 넘기던 절단이 주요 원인이었습니다. 다만 같은 날 조정에는 세 가지가 함께 들어갔습니다. 주장 8개 전부 전달, 판정 기준(확정, 부분, 없음)의 명문화와 근거를 먼저 쓰게 하는 필드 순서 변경, 채점 온도 0입니다. 그래서 정답형 65.3에서 100.0, 오답형 25.7에서 19.4는 세 변경을 합친 결과이며, 반복 2회의 편차는 0.0%p였습니다. 이후 코드를 점검해 보니 임베딩 호출이 0건이고 벡터 테이블도 비어 있었습니다. 그래서 임베딩은 틀려도 플레이어가 고르면 되는 "규칙 대안 추천 순위" 한 자리에만 되살렸습니다. 30문장 비교에서 어간 비교 top-1은 0.300, Gemini 임베딩은 0.967이었습니다. 이 30문장은 에이전트가 쓴 초안이라 팀원 검수를 거친 22문장으로 다시 재어 0.364 대 0.955를 얻었습니다. 로컬용으로는 정확도가 비슷한 모델 중 GPU를 적게 쓰는 쪽을 골랐습니다. 큰 임베딩 모델은 Core와 NPC를 둘 다 밀어냈기 때문입니다. 원인을 좁힌 캘리브레이션 러너와 측정은 평가를 맡은 장민석의 작업이고, 채점 규칙과 프롬프트 변경은 해당 영역을 맡은 팀원들의 작업입니다.

## [04] 인용 보정을 찾아낸 경위와 검증 방법

한 참가자의 밤 채점 화면에서 "내 주장"이 엉뚱한 문장으로 표시된 사례에서 시작했습니다. 기록을 보니 심판 모델의 이유 설명은 2번 후보를 정확히 인용했는데 번호는 1로 적혀 있었습니다. 앞 회차에서 인정된 문장을 잠그는 장치가 이 번호를 키로 쓰기 때문에 표시 오류로 끝나지 않는 문제였습니다. 9월 9일부터 17일까지 저장된 채점 249건을 전수 조사하니, 인용이 있는 181건 중 38건(21%)이 인용과 다른 번호였고 38건 모두 "인용한 후보 번호에서 1을 뺀 값"이었습니다. 재시도로 풀지 않은 이유는 온도 0이라 같은 오답이 반복되기 때문입니다. 같은 249건을 옛 프롬프트와 새 프롬프트로 다시 채점해 비교했고, 판정 분포 일치는 230/249(92%)로 인용 필드가 판정 자체를 흔들지 않음을 확인했습니다. 남은 한계는 인용이 후보와 조금 달라 원래 번호로 떨어지는 11건(약 5%)과, 옛 코드로 채점된 판을 고치지 않았다는 점입니다. 249건 전수 조사와 옛 프롬프트, 새 프롬프트 재채점 비교는 평가를 맡은 장민석이 했고, 엔진 코드 수정은 채점 엔진을 맡은 팀원의 영역입니다.

## [05] provider 전환에서 겪은 문제와 비용을 잰 방법

외부 API로 옮긴 계기는 홈서버와 홈 회선, 정전, 재부팅이 곧 서비스 장애가 된다는 가용성 문제였습니다. 전환은 .env의 provider와 모델 이름 두 필드로 하고 엔진 코드는 바꾸지 않게 했습니다. 붙이는 과정에서 문제가 셋 나왔습니다. SDK 버전에서 temperature 인자가 빠져 한 모델 호출이 실패해 우회 전송으로 고쳤습니다. 구조화 출력의 최대 개수 제한이 외부 API에서 강제되지 않아 계획 역할이 재생성과 폴백을 냈고, 응답 뒤 앞에서부터 잘라내는 결정적 절단으로 막았습니다. 지연 게이트는 n=1과 n=3에서 통과 여부가 뒤집혔습니다. 한 판 비용 0.461달러는 self-play 한 판의 하네스 기록 92건의 실제 프롬프트와 출력을 토큰 계수 API로 세고 정가를 곱한 값입니다. 다만 NPC 발화는 기록에 10건만 남아 실제 발화 수로 환산하면 한 판 약 0.9~1.2달러로 추정됩니다(추정). 프롬프트 캐시를 쓰지 않은 점은 제출 뒤 첫 최적화 후보로 남겼습니다(측정 전). 같은 코드에서 로컬 조합과 비교하면 외부 조합의 이점은 오답형 채점 0점(로컬 14.6점) 하나에 모였습니다. provider 어댑터는 장민석의 담당 범위이며, Anthropic 어댑터도 이 역할에서 붙였습니다.

## [06] 관찰 데이터를 가른 방법과 주장하지 않은 것

게임 DB 248판을 읽기 전용으로 전수 조회해 사람 판을 골라냈습니다. 기준은 참가자 기록 문서에 적힌 판 ID 대조, self-play 로그 제외, 행동 패턴 순이었고, 신원이 불분명한 판은 보류했습니다. 슬라이드의 20건 중 14건은 초기 6판 집계이며, 이후 14판으로 다시 집계했을 때는 적용 규칙 60건 중 AI 계열 48건(80%), 원숭이손 제안 수락 17/21이었습니다. 이 비율은 적용 규칙의 출처 비율이지 참가자 비율이나 AI 신뢰도가 아닙니다. 판수는 고유 참가자 수가 아니고 팀 내부 인원의 판이 섞여 있습니다. 게임 버전도 판마다 달라 경향 주장에 쓰지 않았습니다. 후반 회차 점수 하락도 같은 서술이 다른 점수를 받은 사례가 있어 행동 변화로 해석하지 않았습니다. 사전등록한 본 실험은 AI 제안에 이유를 붙인 조건과 붙이지 않은 조건을 무작위로 배정해 수용률을 비교하는 설계이며, 미실행 상태입니다. 공개 전에는 금지어 검사 스크립트로 스포일러와 운영 세부를 걸렀습니다. 연구 사이트의 실험 설계와 관찰 집계는 평가와 실험 설계를 맡은 장민석의 역할 범위에서 진행했습니다.
