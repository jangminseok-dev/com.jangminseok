## [04] 맡은 범위와 작업 방식

팀 역할 문서에서 장민석은 AI 평가 담당(AI Evaluation Engineer)으로, "이 자리에 어떤 모델을 쓸 것인가"에 숫자를 붙이는 역할을 맡았습니다. 평가 러너(backend/scripts의 run_* 스크립트), 모델 평가 정본 문서, 실측 적립 파일(metrics.yml), Core 선정과 NPC 모델 선정 실험, provider 어댑터, 배포 지표(지연 p50/p95, GPU 상주량)가 이 범위입니다. 프로젝트 초반인 9월 초에는 백엔드와 AI 담당이었고, 9월 14일부터 AI 평가를 맡았습니다. 본선 발표(2026년 10월 17일 예정)에서도 모델 평가 구간과 "숫자, 게이트, 모델 선정" 질문을 맡기로 정해져 있습니다. 인원이 적어 영역을 넘나들며 함께 작업했고, 팀원 전원이 온프레미스 서버 한 대에 SSH로 접속해 코드를 고치며 테스트했습니다. 아래 각 항목의 기여는 이 역할 분담을 기준으로 나눠 적었습니다.

## [03] 합격선을 먼저 정한 이유와 판정 순서

Core(계획, 관리, 채점)를 먼저 확정하고 NPC를 나중에 정한 이유는 실패 비용이 비대칭이었기 때문입니다. Core가 틀리면 세계가 굴러가지 않고 채점이 무너지지만, NPC가 어색한 것은 게임이 돌아가는 채로 고칠 수 있습니다. 실제로 초기에 Core의 질문 답변 역할이 폴백으로 무너진 사례가 있었습니다. 게이트는 스키마 준수율, 폴백률, 극성 쌍(같은 사건을 반대로 묻는 두 문항이 모두 맞아야 통과), 상주량, 지연으로 구성했습니다. 지연을 품질과 별개 축이 아니라 탈락 기준으로 둔 이유는 밤 질문과 밤 채점이 플레이어가 멈춰서 기다리는 자리였기 때문입니다. 지연 값은 단발 측정이 아니라 문항 전체의 p95로 판정했습니다. 재생성이 붙으면 시간이 곱절로 늘어나기 때문입니다. 후보를 한 번에 다 돌리지 않고 프로토콜 호환, 스모크, 본실험(n=3), 동시 상주, 루프 완주의 다섯 단계로 걸렀습니다. 채택은 마지막 루프 완주 단계를 통과한 뒤에만 했습니다. 단일 종합 점수는 가중치가 임의라는 이유로 만들지 않았습니다. 지연 기준값(질문 답변 p95 5초 등)은 통념으로 잡은 값이고 플레이테스트로 검증한 값은 아니라고 문서에 밝혀 두었습니다.

## [03] 동시 상주를 잰 방법과 한계

GPU는 RTX 5060 Ti 16GB 한 장이었습니다. 처음에는 모델 파일 크기로 예산을 추정했지만, 한 후보는 디스크 8.95 GiB인데 실제 상주가 3.06 GiB로 크게 어긋나 이후 예산 판정은 실측 상주량으로만 했습니다. 동시 상주 측정은 NPC 모델을 먼저 올려 운영 상태를 재현하고, Core 후보를 올린 뒤 NPC 호출과 Core 호출을 세 라운드 번갈아 보내면서 매 호출 직후 상주 목록을 찍어 축출과 CPU 오프로드를 확인하는 방식입니다. Core 선정 단계의 측정은 당시 NPC 모델이던 EXAONE 3.5와의 조합이었고, 모델 합계 12.34 GiB, 장치 실측 최고 13,326 / 16,311 MiB(81.7%)에서 축출 0이었습니다. NPC를 Kanana로 바꾼 채택 조합을 같은 방식으로 다시 재니 모델 합계 12.42 GiB, 장치 실측 최고 13,402 / 16,311 MiB였고, 번갈아 호출한 구간의 축출과 CPU 오프로드는 0이었습니다. 두 값은 서로 다른 계측(모델별 상주량 합과 장치 전체 사용량)입니다. 한계도 분명합니다. 세 라운드를 합쳐 약 1분인 단시간 측정이고, 동시 사용자 부하 시험은 하지 않았습니다(측정 전). NPC 41문답 실패 0, 중간값 2.599초는 9월 15일 Gemma를 NPC로 쓴 별도 검사이며, 메모리 저장소를 쓴 유스케이스 시간이라 실제 API와 DB 지연은 빠져 있습니다.

## [05] 채점 점수가 오른 이유와 임베딩을 되살린 자리

플레이테스트 8판에서 정답에 도달해도 점수가 21~42%에 머물렀습니다. 골든 세트 3종(정답형, 절반형, 오답형)을 오프라인으로 채점하는 캘리브레이션 러너를 만들어 원인을 좁혔고, 유사도 상위 3개만 심판에게 넘기던 절단이 주요 원인이었습니다. 다만 같은 날 조정에는 세 가지가 함께 들어갔습니다. 주장 8개 전부 전달, 판정 기준(확정, 부분, 없음)의 명문화와 근거를 먼저 쓰게 하는 필드 순서 변경, 채점 온도 0입니다. 그래서 정답형 65.3에서 100.0, 오답형 25.7에서 19.4는 세 변경을 합친 결과이며, 반복 2회의 편차는 0.0%p였습니다. 다만 이 점수는 골든 세트 답안으로 잰 값입니다. 다음 날인 9월 7일 실제 플레이에서는 점수가 훨씬 낮게 나와, 자동 지표와 실제 플레이가 갈린다는 것을 확인했습니다. 9월 8일 정답률 리뷰는 골든 세트가 정답 문장의 어휘를 그대로 쓴 글이라 사람이 자기 말로 쓴 답과 입력이 달랐다고 봤습니다. 같은 날 재검증에서는 입력 보존, 의미 판정, 정보 전달을 함께 고쳐야 한다고 정리했습니다. 이후 코드를 점검해 보니 임베딩 호출이 0건이고 벡터 테이블도 비어 있었습니다. 그래서 임베딩은 틀려도 플레이어가 고르면 되는 "규칙 대안 추천 순위" 한 자리에만 되살렸습니다. 30문장 비교에서 어간 비교 top-1은 0.300, Gemini 임베딩은 0.967이었습니다. 이 30문장은 에이전트가 쓴 초안이라 팀원 검수를 거친 22문장으로 다시 재어 0.364 대 0.955를 얻었습니다. 로컬용으로는 정확도가 비슷한 모델 중 GPU를 적게 쓰는 쪽을 골랐습니다. 큰 임베딩 모델은 Core와 NPC를 둘 다 밀어냈기 때문입니다. 원인을 좁힌 캘리브레이션 러너와 측정은 평가를 맡은 장민석의 작업이고, 채점 규칙과 프롬프트 변경은 해당 영역을 맡은 팀원들의 작업입니다.

## [05] 인용 보정을 찾아낸 경위와 검증 방법

한 참가자의 밤 채점 화면에서 "내 주장"이 엉뚱한 문장으로 표시된 사례에서 시작했습니다. 기록을 보니 심판 모델의 이유 설명은 2번 후보를 정확히 인용했는데 번호는 1로 적혀 있었습니다. 앞 회차에서 인정된 문장을 잠그는 장치가 이 번호를 키로 쓰기 때문에 표시 오류로 끝나지 않는 문제였습니다. 9월 9일부터 17일까지 저장된 채점 249건을 전수 조사하니, 인용이 있는 181건 중 38건(21%)이 인용과 다른 번호였고 38건 모두 "인용한 후보 번호에서 1을 뺀 값"이었습니다. 재시도로 풀지 않은 이유는 온도 0이라 같은 오답이 반복되기 때문입니다. 같은 249건을 옛 프롬프트와 새 프롬프트로 다시 채점해 비교했고, 판정 분포 일치는 230/249(92%)로 인용 필드가 판정 자체를 흔들지 않음을 확인했습니다. 남은 한계는 인용이 후보와 조금 달라 원래 번호로 떨어지는 11건(약 5%)과, 옛 코드로 채점된 판을 고치지 않았다는 점입니다. 249건 전수 조사와 옛 프롬프트, 새 프롬프트 재채점 비교는 평가를 맡은 장민석이 했고, 엔진 코드 수정은 채점 엔진을 맡은 팀원의 영역입니다.

## [05] provider 전환에서 겪은 문제와 비용을 잰 방법

외부 API로 옮긴 계기는 홈서버와 홈 회선, 정전, 재부팅이 곧 서비스 장애가 된다는 가용성 문제였습니다. 전환은 .env의 provider와 모델 이름 두 필드로 하고 엔진 코드는 바꾸지 않게 했습니다. 붙이는 과정에서 문제가 셋 나왔습니다. SDK 버전에서 temperature 인자가 빠져 한 모델 호출이 실패해 우회 전송으로 고쳤습니다. 구조화 출력의 최대 개수 제한이 외부 API에서 강제되지 않아 계획 역할이 재생성과 폴백을 냈고, 응답 뒤 앞에서부터 잘라내는 결정적 절단으로 막았습니다. 지연 게이트는 n=1과 n=3에서 통과 여부가 뒤집혔습니다. 한 판 비용 0.461달러는 self-play 한 판의 하네스 기록 92건의 실제 프롬프트와 출력을 토큰 계수 API로 세고 정가를 곱한 값입니다. 다만 NPC 발화는 기록에 10건만 남아 실제 발화 수로 환산하면 한 판 약 0.9~1.2달러로 추정됩니다(추정). 프롬프트 캐시를 쓰지 않은 점은 제출 뒤 첫 최적화 후보로 남겼습니다(측정 전). 같은 코드에서 로컬 조합과 비교하면 외부 조합의 이점은 오답형 채점 0점(로컬 14.6점) 하나에 모였습니다. provider 어댑터는 장민석의 담당 범위이며, Anthropic 어댑터도 이 역할에서 붙였습니다.

## [05] 관찰 데이터를 가른 방법과 주장하지 않은 것

게임 DB 248판을 읽기 전용으로 전수 조회해 사람 판을 골라냈습니다. 기준은 참가자 기록 문서에 적힌 판 ID 대조, self-play 로그 제외, 행동 패턴 순이었고, 신원이 불분명한 판은 보류했습니다. 슬라이드의 20건 중 14건은 초기 6판 집계이며, 이후 14판으로 다시 집계했을 때는 적용 규칙 60건 중 AI 계열 48건(80%), 원숭이손 제안 수락 17/21이었습니다. 이 비율은 적용된 규칙의 출처 비율이며 탐색적 집계입니다. 판수는 고유 참가자 수와 다르고 팀 내부 인원의 판이 섞여 있으며 게임 버전도 판마다 달라, 참가자의 경향이나 AI 신뢰도로는 읽지 않았습니다. 후반 회차의 점수 하락도 같은 서술이 다른 점수를 받은 사례가 있어 행동 변화와 구분해 두었습니다. 사전등록한 본 실험은 AI 제안에 이유를 붙인 조건과 붙이지 않은 조건을 무작위로 배정해 수용률을 비교하는 설계이며, 아직 실행 전입니다. 공개 전에는 금지어 검사 스크립트로 스포일러와 운영 세부를 걸렀습니다. 연구 사이트의 실험 설계와 관찰 집계는 평가와 실험 설계를 맡은 장민석의 역할 범위에서 진행했습니다.

## [03] 배포 구성과 AWS를 쓰지 않은 이유

화면은 Vercel에, 서버는 팀의 홈서버에 두고 Cloudflare 터널로 서버 주소를 열었습니다. 데이터베이스는 홈서버의 Docker에서 돕니다. 9월 15일에는 서버를 AWS의 작은 서버(t3.micro)에 두기로 했다가 쓰지 않았습니다. 서버가 홈서버의 AI 모델(Ollama)을 불러야 해서, AWS에 두면 홈서버로 가는 통로를 따로 만들어야 했기 때문입니다. GPU가 달린 AWS 서버를 빌리는 비용도 비교했고, 45일에 1,100~1,600달러로 추정했습니다(추정). 역할 문서에서 배포 검증과 기동 스크립트는 팀원의 영역이고, 최종 배포는 팀장의 신호에 맞춰 진행했습니다. 장민석이 맡은 것은 응답 지연과 GPU 메모리 같은 배포 지표 측정입니다.

## [05] 모델을 고르며 탈락시킨 후보와 이유

생각 기능(thinking)을 켠 후보는 질문 답변 역할의 응답 시간 기준에서 모두 탈락했습니다. 가장 느린 경우는 194,589ms로 기준의 38배였습니다. 평가 러너에서 답을 판정하는 모델(gemma4)도 이 기능이 기본으로 켜져 있어 판정 한 건에 35초가 걸렸고, 러너가 모델을 부르는 13곳에서 기능을 끄도록 고정했습니다. NPC 대사를 쓰는 모델은 처음 고른 EXAONE 3.5가 연구 전용 라이선스여서 Kanana(Apache 2.0)로 바꿨습니다. Gemini는 Core 후보 가운데 기대 방향 일치율이 1.00으로 가장 높았지만, 무료 키 기준의 호출 간격 제한(분당 10회)을 넣으면 응답 시간 기준을 넘어 탈락했습니다. 실제로 무료 키로 바꿔 재 보니 아주 작은 호출도 20~28초가 걸렸습니다. NPC 후보로도 재 보았지만 무료 키는 하루 20번까지만 부를 수 있어 뺐습니다.

## [06] 시험 문항과 실제 플레이의 결과가 뒤집힌 일

채점 역할을 재는 시험 문항을 직접 만들었을 때는 기준 모델(gemma3)이 채택 후보(gemma4)를 1.00 대 0.67로 앞섰습니다. 그런데 실제 플레이 제출문에서 뽑은 14개 문항으로 바꾸니 0.36 대 0.57로 뒤집혔습니다. 시험 문항을 직접 쓰면 실제 사용과 다른 결과가 나올 수 있다는 것을 수치로 확인한 일입니다. 평가 러너의 결함도 하나 찾아 고쳤습니다. 외부 API를 고르고도 모델 이름이 로컬용 기본값이면 호출이 실패하는데, 그 실패가 0점으로 집계되고 있었습니다. 잘못 붙은 기록 두 줄을 되돌리고, 모델 이름이 맞지 않으면 호출하기 전에 바로 멈추게 고쳤습니다.

## [04] 테스트와 검사를 돌린 방식

팀의 테스트는 가짜 AI와 테스트 전용 데이터베이스로 돕니다. 데이터베이스 이름이 _test로 끝나지 않으면 실행을 거부해, 실제 데이터를 건드리지 못하게 했습니다. 통과한 테스트는 9월 6일 뼈대 단계 48개, 9월 10일 386개, 9월 19일 1,059개로 늘었습니다. 검사는 스크립트 하나가 테스트, 모듈 의존 방향 검사(import-linter 계약 4개), 금지어 검사를 차례로 돌립니다.
