# JB Silver Connect 보강 설명

## [01] 3일 동안 범위가 바뀐 과정과 본인 역할

처음부터 지금의 다섯 기능이었던 것은 아닙니다. 첫날 초기 커밋에는 적금 제안, 번호표 예약, 피싱 문자 판별, 날씨와 잔액을 읽어 주는 일일 브리핑, 지점 찾기, 이자 리포트, 대화까지 일곱 개 컨텍스트가 있었습니다. 둘째 날 저녁 커밋에서 적금, 피싱, 이자 리포트를 지우고 법인 사무 안내와 대기열을 새로 세웠습니다. 시연 시나리오를 "말로 상담하고, 번호표를 받고, 창구에서 호출된다"는 한 흐름으로 좁히면서 흐름에 들어가지 않는 기능을 걷어 낸 결과입니다. 직원 화면도 처음에는 admin이라는 이름으로 만들었다가 창구(teller)로 바꿨고, 대기실 호출 화면(display)은 둘째 날에 추가했습니다. 네이버 지도 검색 어댑터는 마지막 날 새벽에 붙였습니다. 백엔드 전체와 프론트 앱 3개는 장민석이 직접 구현했습니다.

## [02] 레이어 규칙을 어떻게 강제하고 확인했나

setup.cfg에 import-linter 계약 두 개를 두었습니다. 하나는 다섯 컨텍스트 각각에 대해 adapter, app, domain 순서의 layers 계약이고, 다른 하나는 shared_kernel이 core나 apps를 import하지 못하게 막는 forbidden 계약입니다. 의존성 조립을 맡는 dependencies 폴더는 일부러 레이어 목록에서 뺐습니다. 조립 루트는 모든 층을 알아야 하므로 검사 대상에 넣으면 계약이 성립하지 않기 때문입니다. 컨텍스트끼리 연결할 때는 상담(chat) 쪽 app 계층에 대기열 등록 포트를 두고, 그 구현체를 adapter 계층에 두어 대기열 컨텍스트의 등록 유스케이스를 호출하게 했습니다. 예약 컨텍스트도 같은 방식으로 대기열에 등록하고 취소 시 제거합니다. 코드 규칙으로는 staticmethod, property, dict[str, Any] 반환, 타입에 따른 if 분기를 금지했습니다. 예를 들어 창구 종류는 enum 멤버가 번호표 접두(법인은 B)를 직접 들고 있어 분기 없이 번호를 만듭니다. 최신 코드 기준으로 테스트 26개가 통과하고 import-linter 계약 2개가 모두 지켜집니다. 다만 테스트는 대기열, 예약 취소, 법인 안내, 고객 목록에 몰려 있고 상담과 지점 찾기 유스케이스 테스트는 없습니다.

## [03] 폴백 체인의 구현 세부와 드러난 약점

각 LLM 어댑터는 키가 빈 문자열이면 곧바로 예외를 던지는 가드를 가지고 있어, 키가 없으면 네트워크 호출 없이 다음 순위로 넘어갑니다. SDK는 generate 안에서 지연 import하므로 패키지가 설치되지 않은 환경에서도 서버가 뜹니다. 체인은 lru_cache로 한 번만 조립되고, 호출부는 LlmPort 하나만 주입받습니다. 지점 검색도 같은 모양의 FallbackMapAdapter로 네이버 다음에 Mock을 두었습니다. 초기에는 피싱 판별 컨텍스트가 자기만의 LLM 포트와 폴백 어댑터를 따로 가지고 있었는데, 컨텍스트마다 같은 코드가 반복되는 문제가 있어 core 공용 포트로 모았습니다. 약점도 분명합니다. Gemini와 Groq 클라이언트가 동기 호출이라 async 함수 안에서 이벤트 루프를 막을 수 있고, 모든 예외를 삼키고 마지막 오류만 다시 던지므로 어느 모델이 답했는지 로그가 남지 않습니다. 또 Mock은 고정된 한 문장만 돌려주기 때문에 키가 하나도 없으면 창구 브리핑 JSON 파싱이 실패하고 기본값 카드("상담 요청", 신분증)가 나갑니다. 흐름은 끝까지 돌지만 브리핑 내용은 비어 있는 셈입니다. 응답 시간이나 폴백 발생 빈도는 기록하지 않았습니다(측정 전).

## [04] Mock 어댑터를 어디까지, 어떻게 만들었나

Mock은 단순히 빈 값을 돌려주는 대신 시연에 필요한 규칙을 담았습니다. 법인 사무 안내 Mock은 사업자등록, 법인설립등기, 법인 인감증명서, 법인 통장 개설 네 업무와 부동산 담보대출용 네 업무를 주제별 dict로 나누고, 각 업무에 필요 서류와 예상 비용, 발급 기관 후보를 넣었습니다. 사용자 좌표에서 기관까지 거리를 계산해 가까운 순으로 세 곳을 추천합니다. 테스트는 서울 좌표에서는 종로세무서가, 전주 좌표에서는 전주세무서가 가장 먼저 나오는지, 알 수 없는 주제는 법인 사무로 돌아가는지 확인합니다. 고객 목록 Mock은 일반 고객과 법인 고객 두 명을 두고 모르는 ID는 일반 고객으로 돌립니다. 예약은 같은 지점에 활성 번호표가 있으면 새로 발권하지 않고 기존 것을 돌려줍니다. 저장소는 모두 dict 기반 메모리 저장소라 서버를 다시 켜면 대기열과 상담 기록이 사라집니다. 법인 안내의 비용과 서류는 코드에 직접 적어 둔 큐레이션 값이며, 실제 서비스라면 정부24나 기관 API 어댑터로 바꿔야 합니다. 설계 문서의 다음 단계에는 Supabase 영속성과 실제 날씨, 음성 합성 연결이 적혀 있었지만 구현하지 않았습니다.

## [05] 대기열 상태 전이와 자동 파기의 구현 방식

대기열 항목은 대기, 현장 도착, 호출 세 상태만 가집니다. 전이 메서드는 현재 상태가 맞지 않으면 예외를 던지지 않고 조용히 무시하게 했습니다. 창구 직원이 버튼을 두 번 누르거나 폴링 사이에 상태가 바뀌어도 화면이 오류로 멈추지 않게 하려는 선택입니다. 자동 파기는 별도 스케줄러 없이 목록을 조회할 때 만료 여부를 검사해 지우는 방식입니다. 창구 화면이 5초마다, 호출 화면이 2초마다 목록을 가져가므로 사실상 폴링이 청소 주기를 대신합니다. 따라서 아무 화면도 열려 있지 않으면 만료 항목이 그대로 남습니다. 대기번호와 도착 예상 시간은 엔티티에 저장하지 않고 목록 안의 위치로 매번 계산합니다. 앞사람이 빠지면 번호가 당겨지는 단순한 방식이며, 도착 예상은 앞선 인원 한 명당 5분으로 잡은 고정 추정치입니다(실측 아님). 대기열에 들어갈 때는 고객 이름과 브리핑 내용을 스냅샷으로 복사해 두어, 대기열 컨텍스트가 상담 컨텍스트의 엔티티를 참조하지 않게 했습니다. 학습 초기라 AI 코딩 도구(Claude Code)가 제안한 폴링을 WebSocket과 비교하지 않고 택했습니다. 3일짜리 시연이고 화면이 3개뿐이라 동작에는 문제가 없었지만, 창구 화면은 최대 5초, 호출 화면은 최대 2초 늦게 상태를 반영하고, 화면이 늘면 요청도 그만큼 곱절로 늘며, 만료 정리가 폴링에 묶여 있다는 약점이 있습니다. 지금 다시 만든다면 서버가 변경을 밀어 주는 SSE로 바꾸고, 만료 정리는 별도 작업으로 분리하겠습니다.

## [06] 창구 브리핑을 구조화한 방법

상담 내용을 창구로 넘길 때 LLM에 목적, 관련 상품, 금액, 필요 서류, 특이사항, 직원 조언, 창구 종류 일곱 필드의 JSON만 출력하라고 지시합니다. 모델이 코드펜스로 감싸 보내는 경우가 있어 먼저 펜스를 벗기고, JSON이 깨지면 카드 전체를 기본값으로, 필드 하나가 비면 그 필드만 기본값으로 채웁니다. 창구 종류는 정확히 corporate일 때만 법인으로 보고 나머지는 일반으로 정규화해, 모델이 엉뚱한 값을 내도 번호표 접두가 틀리지 않게 했습니다. 요약이 틀릴 수 있다는 점을 고려해 고객이 실제로 한 말만 이어 붙인 원문도 카드에 함께 남깁니다. 예약 화면의 메모도 같은 원칙으로, AI 한 문장 요약은 특이사항에, 입력 원문은 그대로 따로 보관하며 테스트로 이 동작을 확인합니다. 음성 입력은 브라우저 Web Speech API를 한국어로 설정하고, 중간 결과 없이 한 문장이 끝나면 입력창을 거치지 않고 곧바로 전송합니다. 타이핑 단계를 없애려는 선택입니다. 지원하지 않는 브라우저에서는 마이크 버튼이 나타나지 않습니다. 법인 서류 안내나 번호표 버튼은 대화 속 키워드 포함 여부로 띄우는 단순 규칙이라 표현이 달라지면 놓칠 수 있습니다. 고령 사용자 대상 사용성 조사나 요약 정확도 평가는 하지 않았습니다(측정 전).
