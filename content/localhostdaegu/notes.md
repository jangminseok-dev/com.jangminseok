## [04] 주제를 좁힌 과정과 장민석의 역할

처음 검토한 방향에는 소상공인 매출 증빙도 있었지만, 실제 매출 데이터를 구할 수 없어 제외했습니다. 대신 트랙 예시 가운데 청년창업 금융 연결과 골목상권 AI 컨설팅을 묶어 "창업 금융 네비게이터"로 정했습니다. 대회 공고 원문을 확인해 AI와 블록체인을 동시에 구현해야 한다는 조건이 없다는 것을 확인했고, 블록체인 앵커링은 범위에서 빼고 상담자료의 sha256 해시만 남겼습니다. 9월 18일에는 주 동선을 위험 진단에서 "계약 전 창업자금 사전상담"으로 바꿨습니다. 계약 뒤에는 조건을 바꾸는 데 비용이 들기 때문입니다. 주제와 범위에 대한 이 결정들은 팀이 함께 내렸습니다. 백엔드는 새로 쓰지 않고, 팀원이 이전에 만든 서울 상권 서비스 Metabole의 코드를 옮겨 와 서울에 묶인 부분을 대구 기준으로 바꿔 진행했습니다. Metabole이 헥사고날 구조라 지역에 묶인 어댑터만 바꿔 옮길 수 있었습니다. 장민석의 개인 프로젝트 RedOceanMap에서 참고한 것은 결론은 AI가 아니라 코드가 쓴다는 원칙, 한 문장 입력으로 시작하는 첫 화면 방식, 결정 이유를 기록으로 남기는 방식입니다. 장민석은 팀장이자 PM과 아키텍트로서 API 계약, 배포 구조, 범위와 우선순위, 리뷰와 병합 승인, 제안요약서와 시연 대본, 접수를 맡았고, 9월 18일 분담 이후 DB 스키마 확장과 ERD 문서화, 외부 API 키 관리도 담당했습니다. 9월 15일부터 17일까지의 초기 포팅과 기능 구현은 팀 공동 작업이었고, 장민석은 그중 PM과 아키텍트 역할에 맞게 API 계약과 배포 구조, 범위와 우선순위를 맡았습니다.

## [03] 계약 우선 분담을 운영한 방식

9월 18일 오전, 장민석은 구현을 시작하기 전에 세 가지 계약을 먼저 정했습니다. 분석 요청에 연도를 받는 필드, 재무 응답에 담을 계산 가정 정보(6개월 고정비, 시나리오 배수 등), 지표 응답에 담을 분모와 기간, 건수 필드입니다. 충돌을 줄이려고 프론트의 공용 타입 파일과 백엔드 진입 파일은 기존 줄을 고치지 않고 추가만 하도록 규칙을 두었고, 같은 분석 API를 건드리는 기간 일치와 AI 진행 표시 두 기능은 한 팀원에게 몰아 맡겼습니다. 개발 기록과 인수인계 문서는 장민석이 하루 한 번 통합했습니다. 팀원 모두 서버 한 대에 SSH로 접속해 작업했기 때문에 커밋 작성자는 서버 계정 하나로 남아 있고, 실제 담당은 작업 목록(WBS)과 개발 기록의 담당 표로 구분했습니다. 분담 전에는 백엔드 460개 파일(약 13,600줄)을 세 영역으로 나눠 AI 리뷰어 셋이 동시에 리뷰했고, 세 영역 모두 Critical 결함 없이 "수정 후 병합" 판정이 나온 뒤 main에 합쳐 공통 기준점으로 삼았습니다. 이 리뷰는 팀 공동 작업입니다. 분담 뒤에는 모두 같은 서버에서 작업하며 변경을 main에 차례로 올렸습니다. 처음 정한 9월 19일 18:00 코드 프리즈는 9월 18일 결정으로 해제하고 개발을 이어 갔습니다. 계획대로 흘러가지 않은 부분도 기록으로 남겼습니다.

## [05] 금액은 코드가, 해석은 AI가 쓰게 만든 구현

리포트는 섹션 단위로 실시간 전송되는데, 섹션 제목, 위험도 점수, 지표표, 매칭 상품 목록은 코드가 먼저 내보내고 AI는 해석 문단만 씁니다. AI 호출이 실패하면 섹션은 대체 문구로 채워지고 계산 결과는 그대로 남습니다. 운영 주소에서 가상 고객 10명을 돌렸을 때 상담자료 첫 문단이 바로 위 표의 수치를 두고 "수치가 없다"고 쓰는 문제가 전원에게서 나왔습니다. 계획 수치를 프롬프트에 그대로 싣고 "수치가 없다고 쓰지 마라"를 명시하자, 같은 10명을 로컬에서 빌드한 화면과 운영과 같은 백엔드로 다시 돌렸을 때 이 문단이 0건이 됐습니다. 가상 고객 테스트와 이 수정은 팀원이 맡았습니다. 이때 금액 표기도 화면과 같은 만원 단위로 맞췄고, 지표가 하나도 없는 업종은 AI를 부르지 않고 "집계되지 않았을 뿐 나쁘다는 뜻이 아니다"를 코드가 씁니다. 그 밖에 본문 인용 번호가 하단 참고 자료와 어긋나 문서 제목으로 인용하게 바꿨고, 질문이나 검색 문서 속 지시를 따르지 않도록 막고 질문을 500자로 제한했습니다. 이 원칙은 9월 15일 팀 결정(DEC-007)으로 정했고, 장민석은 아키텍트로서 이를 API 계약에 반영했습니다.

## [05] 리포트 모델과 오프라인 대체 모델 평가

외부 API 한도, 비용, 네트워크 장애에 대비해 로컬 모델이 같은 일을 얼마나 해내는지 운영과 같은 시스템 지시, 프롬프트, 근거로 쟀습니다. 리포트 LLM은 후보당 28건을 제목 금지, 분량 상한, 프롬프트에 없는 숫자 사용, 인용 제목의 실존 여부, 위험 등급을 바꿨을 때 첫 문장 방향 같은 결정론 게이트로 채점했습니다. 운영 모델과 gemma4:12b가 게이트 통과율 1.000, 숫자 환각 0건이었고 exaone3.5는 0.536이었습니다. 임베딩은 코퍼스 3,448건과 질문 80건으로 Top-1 정확도를 쟀고 로컬 qwen3-embedding 2560차원이 0.762, Gemini가 0.700~0.738이었습니다. 그래도 운영은 Gemini를 유지했고, 오프라인 전환은 환경변수 2개와 약 3분 재색인으로 가능하게 차원만 맞춰 두었습니다. pgvector HNSW 인덱스의 vector 타입이 2000차원 상한이라 halfvec을 썼습니다. 한계는 평가 질문 80건이 자동 생성된 미검수 셋이고, 이후 정답 공고가 만료돼 다시 뽑아야 한다는 점입니다. 자동 폴백도 설계하지 않았습니다. 평가와 어댑터 구현은 팀원이 맡았습니다.

## [05] 스키마를 추가만으로 확장한 이유와 검증

금융상품, 외부 데이터셋과 지표, 상담 세션 네 영역 10테이블을 alembic 리비전 하나로 넣었고, 이 리비전은 create_table 10건과 create_index 8건뿐이며 기존 19테이블에 대한 컬럼 변경이나 삭제는 0건입니다. 기존 상품 매칭 함수와 라우터도 고치지 않는 것을 인수 기준으로 두어, 기존 매칭 API 응답이 바뀌면 회귀로 보았습니다. 금융상품은 DB를 정본으로 하고 수기 JSON은 시드 입력으로 쓰며, DB가 비었거나 연결에 실패하면 JSON으로 폴백하고 경고를 남깁니다. 외부 데이터셋 테이블은 출처 제한과 집계 방식 메모를 NOT NULL로 두어, 출처 없는 지표가 들어올 수 없게 스키마로 강제했습니다. 다만 이 두 테이블은 대구 빅데이터활용센터 데이터를 받지 못해 비어 있고, ERD 문서에 "자리가 있다고 데이터가 있는 것은 아니다"라고 밝혔습니다. FK가 양쪽 모두 없는 고립 테이블 2건(전국 금리, 정책 공고)은 새로 만든 테이블이 아니라 기존 테이블이며, 억지로 엣지를 만들지 않고 새 고립 테이블이 생기면 실패하는 테스트로 감시했습니다. 다음 날 어린이집 테이블 2개가 더해져 지금은 31개입니다.

## [05] 배포 구조를 정하며 미리 막은 문제

분석 요청을 메모리 저장소에 두는 구조라 워커를 늘리면 요청 생성과 이벤트 구독이 다른 프로세스로 갈라져 404가 납니다. 그래서 uvicorn 워커를 1개로 고정하는 것을 배포 조건으로 적었고, 여러 워커가 필요해지면 Redis 어댑터로 바꿔야 한다는 점도 남겼습니다. 스트리밍은 서버가 X-Accel-Buffering: no 헤더를 보내고 프록시 버퍼링을 끄도록 런북에 적었습니다. 프론트의 API 주소 환경변수를 빠뜨리면 화면이 조용히 가짜 응답으로 떨어지는 함정도 런북에 기록했습니다. 배포를 막던 CORS 고정값은 환경변수로 뺐고, 운영에서 두 오리진만 허용되고 다른 오리진은 거부되는지 확인했습니다. 첫 배포 뒤 운영 도메인과 터널을 거쳐 첫 이벤트 0.2초, 첫 AI 문단 1.4초에 도착하고 12초대까지 순서대로 이어지는 것을 통합 테스트 항목으로 확인했습니다. 수집 실패 오류 메시지에 요청 주소가 통째로 담겨 외부 API 키 하나가 서버 로그에 남은 일이 있었고, 모든 외부 연동에서 오류 메시지의 키를 지우도록 고친 뒤 해당 키를 재발급했습니다. 배포 구조 확정과 키 관리는 장민석, 실제 백엔드와 프론트 배포 실행은 팀원이 맡았습니다.

## [05] 위험 점수 표현을 바꾼 근거와 데이터 한계

위험 점수는 폐업률, 점포 수, 점포 증감률 각각의 지역 간 백분위를 0.4, 0.4, 0.2 비율로 섞은 0~100점입니다. 산식상 점포가 순증해도 점수가 오르므로 실패 확률로 읽힐 수 있는 값이 아니었고, 그래서 "대구 142개 동 가운데 몇 번째"라는 상대 순위로 바꿨습니다(DEC-024). 142는 행정동 144곳 중 경계 데이터가 있는 수입니다. 데이터를 직접 조회해 보니 성내2동의 2025년 카페 폐업 182건 가운데 137건이 개업 30일 이내 종료였고, 이를 단기 영업 인허가로 보고 폐업률과 위험도 집계에서 뺐습니다. 이 규칙으로 폐업률이 100%를 넘던 동 2곳이 사라졌습니다. 인허가 기록은 과거 폐업을 포함한 이력이지 현재 영업 점포 수가 아니며, 카드 소비와 생활인구, 실매출은 없습니다. '성장률'도 매출이 아니라 점포 증감률이라 명칭을 바로잡았습니다. 표현 수위 원칙은 장민석이 정했고, 화면의 분모 설명과 라벨 구현은 팀원이 맡았습니다. 상대 순위 표기의 화면 구현은 데이터 신뢰 표시를 맡은 팀원의 영역입니다.

## [03] 배포 구성의 세부와 운영 사고

화면은 Vercel에, 서버는 팀이 관리하는 GPU 컴퓨터 한 대에 두고 Cloudflare Tunnel로 열었습니다. 서버는 Docker가 아니라 시스템 서비스(systemd)로 띄워 컴퓨터를 켜면 자동으로 시작됩니다. Docker에는 데이터베이스와 Redis, Neo4j만 두고 포트는 모두 컴퓨터 안에서만 열었습니다. 배포를 실행한 것은 팀원입니다. 운영 사고가 한 번 있었습니다. 9월 19일 밤 손으로 다시 시작한 서버에 접속 허용 설정(CORS) 환경변수가 빠져, 운영 화면의 요청이 약 1시간 동안 막혔습니다. 명령줄로 직접 호출하면 정상이어서 알아채기 어려웠습니다. 손으로 띄운 서버를 내리고 원래의 시스템 서비스로 다시 띄운 뒤, 다시 시작할 때는 반드시 서비스 명령을 쓴다고 운영 문서에 적었습니다.

## [04] 테스트 구성과 개수

백엔드는 pytest로 도메인 규칙, 주소별 응답 형식, 외부 연동, 데이터베이스 통합을 검사하고, 화면은 Vitest와 브라우저 자동 테스트로 검사했습니다. 백엔드 테스트는 196개(9월 16일)에서 603개로, 화면 테스트는 77개에서 226개로 늘었습니다. 테스트가 개발용 데이터베이스를 건드려 수집할 때마다 같은 22건이 반복해서 만료 처리되는 문제가 있었습니다. 테스트 전용 데이터베이스를 자동으로 만들고, 이름이 _test로 끝나지 않으면 테스트를 멈추게 해서 막았습니다. 부하 테스트는 하지 않았습니다(측정 전).
