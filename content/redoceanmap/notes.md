## [03] 구조 계약 5종의 실제 내용과 CI를 두지 않은 이유

import-linter 계약은 다섯 가지입니다. 앱 내부의 계층 순서(adapter, app, domain), 스포크끼리의 직접 참조 금지, 허브가 스포크를 참조하지 않는 허브 격리, app과 domain 계층이 FastAPI, SQLAlchemy, Ollama, LangChain을 import하지 못하게 하는 프레임워크 격리, domain 계층이 pydantic조차 모르게 하는 도메인 순수성입니다. GitHub Actions CI는 실제로 구축해 첫 실행 통과까지 확인한 뒤 제거했습니다. 당시에는 AI 코딩 도구(Claude Code)와 논의해 1인 개발 단계에서는 로컬 pytest와 lint-imports 수동 실행으로 충분하다고 보았습니다. 수동 실행을 빠뜨리면 계약 위반을 놓칠 수 있다는 한계가 있어, 이후 프로젝트인 이 포트폴리오 사이트(jangminseok.com)에서는 테스트와 import-linter를 push마다 도는 CI 게이트로 두었습니다. RedOceanMap에서는 그 대신 계약 검사를 테스트 실행과 같은 도구로 묶어 변경할 때마다 함께 돌렸고, 마일스톤 완료 기록마다 "계약 5 KEPT"를 검증 항목으로 남겼습니다. 계약이 설계를 바꾼 사례도 있습니다. 검색 평가 러너는 주식과 상권 유스케이스를 함께 조립해야 해서 chat 앱 안에 두면 스포크 상호 독립 계약에 걸렸습니다. 그래서 러너를 앱 밖의 합성 루트 위치에 두었습니다. 관심 목록 보드에서 종목 신호가 필요했을 때도 추천 앱이 주식 앱을 직접 부르지 않도록 허브에 StockStatusPort를 새로 만들었고, 이 포트는 이후 알림 메일에서도 재사용해 보드와 메일이 같은 값을 보여 주게 됐습니다.

## [05] 결정론 가드를 만든 과정과 구현 방식

가드의 출발점은 실서비스 페르소나 테스트였습니다. 테스트 계정으로 초보, 전문가, 손실 중인 투자자 등의 역할을 맡아 단발 질문 30건씩 2회, 멀티턴 20개 시나리오 55턴을 1회 돌렸습니다. 실패는 세 부류였습니다. 종합점수 '주의' 등급(44.9점) 상권을 "강력히 추천"한 사실 반전, 상권을 특정하지 못하면 422 오류 JSON이 사용자에게 그대로 보이는 문제, 자기 서비스의 적중률을 묻자 다른 회사 모델이라고 답한 자기 부정입니다. 원인은 모델이 "50점은 서울 평균"이라는 점수의 의미를 모른 채 숫자를 자유롭게 서술했기 때문이었습니다. 그래서 점수마다 "서울 평균 미달" 같은 방향 문장을 코드가 컨텍스트에 넣고, 주의 또는 위험 등급이면 추천 어휘를 후처리로 바꾸고 등급 고지를 첫 문단에 삽입했습니다. 조건 질의는 LLM을 거치지 않고 랭킹 집계를 코드가 정렬해 답하게 바꿨습니다(62초 오류에서 1.5초 정답). 가드는 답변 후처리 계층에 모으고 평가 채점기와 같은 정규식을 쓰도록 판정 어휘의 정의처를 하나로 묶었습니다. 가드를 통과한 답이 평가에서 떨어지면 둘이 어긋났다는 신호가 되기 때문입니다.

## [05] 가드가 실패를 가린 사고: 컨텍스트 창 초과

전년 대비 매출 열을 상권 선택 단계 프롬프트에 추가하자 프롬프트가 4,042토큰에서 4,178토큰으로 늘었습니다. Ollama의 기본 컨텍스트 창이 4,096토큰이어서 초과분이 앞에서부터 잘렸고, 맨 앞의 JSON 형식 지시문이 통째로 사라졌습니다. 모델은 상권 표를 그대로 옮겨 적었고, 상권 코드 반환이 40건 중 40건 성공에서 44건 중 0건으로 떨어졌습니다. 그런데 지역명 어간을 매칭하는 결정론 지역 가드가 추천 상권을 보정해 주는 바람에 지역 적중률 지표는 1.0으로 정상처럼 보여 지표만으로는 드러나지 않았습니다. 재현 실험에서 창 4,096에서는 실제 처리된 프롬프트가 2,050토큰으로 잘려 형식이 깨졌고, 8,192에서는 4,179토큰 전량이 들어가 정상 JSON이 나왔습니다. 조치는 오케스트레이터에 창 크기 8,192를 명시하고, 서버가 돌려주는 실제 처리 토큰 수가 창에 가까워지면 경고를 남기게 한 것입니다. 회귀 테스트로 이 조건을 고정했습니다. 결과 지표만으로는 가드 뒤의 실패가 보이지 않는다는 점, 그래서 가드가 얼마나 개입했는지를 따로 감시해야 한다는 점이 이 사고의 교훈입니다.

## [05] 골든셋 평가 하네스의 설계 선택

평가는 러너와 게이트로 나뉩니다. 러너만 실제 LLM을 호출해 케이스별 단계 호출, 응답, 지연을 trace 파일로 남기고 커밋합니다. 게이트는 그 trace를 순수 함수 채점기로 다시 채점하므로 LLM 없이 기본 테스트에 포함됩니다. 러너는 운영 코드를 고치지 않고 오케스트레이터를 "실제 호출과 기록" 프록시로 바꿔 끼우며, 데이터 포트는 실 DB 덤프 스냅샷으로 고정해 DB가 분기마다 갱신돼도 정답이 흔들리지 않게 했습니다. 지표는 의도 분류 정확도, 지역 적중률, 멀티턴 승계율, 인용 커버리지 등이고, 서울 외 지역 차단, 매매 지시 금지 문구, 지하철 노선 같은 입지 창작 금지는 절대 규칙입니다. baseline을 바닥으로 둔 것은 실측 때문입니다. 같은 조건 4회 실행에서 종목 질의 정확도가 0.767에서 0.833 사이를 오갔는데, 이 폭이 회귀 허용치 3%p보다 넓어 최고 기록을 기준으로 삼으면 평소 수준의 실행도 실패로 떨어집니다. 그래서 관측 최소값을 기준선에 넣었습니다. 한계도 분명합니다. 스냅샷 통계 일부가 합성이라 사실성이 아니라 근거 준수를 재며, 유용함 같은 주관 품질은 재지 않습니다.

## [05] 라이선스 문제로 생성 모델을 교체한 과정

기존 생성 모델 EXAONE 3.5 7.8B는 연구 전용 라이선스여서 공개 서비스 전에 교체해야 했습니다. 후보는 8GB VRAM에 컨텍스트 창 8,192의 KV 캐시까지 올릴 수 있는 크기로 한정했고, 같은 골든셋 러너로 EXAONE 기준선과 비교했습니다. 1차 실측에서는 게이트를 그대로 통과한 후보가 없었습니다. Llama 3.1 8B는 컨텍스트에 없는 지하철 노선을 지어냈고 숫자 환각이 2건이었습니다. Kanana 1.5 8B는 환각은 없었지만 인용 커버리지 0.316, 멀티턴 승계율 0.667로 지시 준수가 약했습니다. Gemma 4 e4b(사고 모드 끔)는 환각, 잘림, 절대 규칙 위반이 모두 0이어서 후보로 확정했고, 남은 회귀는 EXAONE에 맞춰 다듬은 프롬프트를 덜 따르는 문제로 보고 프롬프트를 다시 조정했습니다. 사고 모드를 켜면 답변당 수십 초가 걸려 끄는 설정을 새로 만들었습니다. 재조정 과정에서 모델이 컨텍스트 블록의 항목 순서를 근거 번호로 오해하는 문제가 드러나, 쓸 수 있는 근거 번호 목록을 코드가 컨텍스트 끝에 붙였습니다. 교체 뒤 라이선스가 출력물에도 걸린다는 점 때문에 기존 뉴스 감성 라벨 약 10.5만 건도 새 모델로 다시 매기기로 했습니다.

## [05] 하이브리드 검색을 기각하고 결론을 정정한 과정

검색 품질 지표가 없던 상태에서 골든셋 40문항(주식 25, 상권 15)을 만들고, 두 시스템의 상위 후보 합집합을 한 번에 라벨링하는 TREC pooling 방식으로 1,120건에 0, 1, 2 등급을 매겼습니다. 라벨은 사람이 아니라 외부 LLM이 붙였고, 이 사실을 평가 문서에 명시해 해석할 때 참작하게 했습니다. 서비스 모델이 자기 검색을 심판하는 순환은 아니라고 판단했지만 사람 검수 표본이 없다는 한계는 남습니다. 하이브리드는 전체로는 +0.018이었지만 주식 +0.051, 상권 -0.039로 카테고리마다 방향이 반대였고, 게이트 조건 그대로 기각했습니다. 실험 경로 코드는 재도전을 위해 남겼습니다. 이후 임베딩을 embeddinggemma로 바꾸자 새 모델이 찾은 상위 10건 중 58%가 라벨이 없는 문서여서 0점 처리됐고, nDCG@5가 0.443으로 급락한 것처럼 보였습니다. 편향된 값으로 기준선을 낮추지 않기로 하고 미라벨 후보 707건을 추가 라벨링한 뒤 같은 라벨로 네 조합을 다시 채점했습니다. 그 결과 새 임베딩에서는 하이브리드가 순수 벡터보다 낮아, 결론을 "임베딩이 약할 때만 이득"으로 고쳤습니다. 공시 청킹(표 행 단위 분할)도 같은 방식으로 측정해 기각했습니다.

## [05] 배포 구조를 나눈 이유와 전환 절차

처음 프로덕션 compose 전환 점검에서 잡은 결함 6건은 공개 터널 컨테이너 누락, 호스트 이름 해석 설정 누락으로 LLM 서버와 상권 DB가 동시에 끊기는 문제, 상권 DB 주소가 localhost라 컨테이너가 자기 자신을 가리켜 메인 DB로 조용히 폴백하는 문제, 인증이 걸린 경로를 헬스체크로 써서 영구 unhealthy가 되는 문제, 다른 프로젝트와 겹친 서비스 중복 선언, 프로젝트명이 바뀌며 컨테이너 이름에 의존하던 cron이 깨지는 문제였습니다. 이후 k3s로 옮길 때는 백엔드, 인증 서버, 터널, 블로그, 도커 기반 cron만 옮기고 DB, Redis, 그래프 DB, 자동화 도구는 compose에 남겼습니다. 클러스터 안에 DB 이름의 셀렉터 없는 Service와 EndpointSlice를 두어 앱의 연결 문자열을 하나도 바꾸지 않았고, 나중에 관리형 DB로 옮길 때는 EndpointSlice만 교체하면 되게 했습니다. 컷오버는 백업, 포트 개방, 기존 컨테이너 중지, 매니페스트 적용, 공개 도메인 확인 순으로 진행했고, 롤백은 이전 compose 파일로 되돌리면 되도록 DB 볼륨은 건드리지 않았습니다. 현재 CronJob 매니페스트는 11종입니다. 초기 로드맵에서는 K8s를 과설계로 분류했지만, 배포와 정기 작업, 재시작을 한곳에서 보려는 운영 편의 때문에 단일 노드 k3s만 예외로 두고 옮겼습니다. 서비스 규모를 키우려는 목적은 아닙니다.

## [05] LangGraph와 QLoRA를 검토하고 넣지 않은 과정

새 라이브러리는 네 가지를 확인한 뒤에 넣습니다. 이 기술이 없으면 하기 어려운 작업이 실제로 있는지, 도입 범위를 최소로 좁혔는지, 지연과 메모리를 측정하고 허용선을 정했는지, 한 파일만 바꾸면 뺄 수 있는지입니다. LangChain과 pgvector는 이 확인을 통과해 들어왔습니다. LangGraph는 2026년 7월에 비교 질문 전용 경로로 설계까지 했습니다. 다만 사용자가 그런 질문을 실제로 하는지 세어 본 뒤에 코드를 쓰기로 문서에 적어 두었습니다. 8월에 이 경로가 쓸 Neo4j 그래프 검색의 착수 여부를 판정하면서, 그때까지 쌓인 질문 129건을 모두 분류했습니다. 개발자가 테스트로 넣은 질문도 섞여 있습니다. 벡터 검색 한 번이나 SQL 조인으로 답할 수 있는 질문뿐이었고, 세 단계 이상 따라가야 답할 수 있는 질문은 0건이었습니다. 대표 질문 10개 중 3개 이상이면 착수한다는 조건에 못 미쳐 그래프 검색을 보류했고, 그 앞 단계인 LangGraph 경로도 함께 보류했습니다. 대화 이력은 이미 PostgreSQL에 있어서 LangGraph의 체크포인터를 넣으면 저장소가 둘이 되고, 지금 코드의 반복은 JSON 파싱이 실패했을 때 한 번 다시 시도하는 것이 전부라는 점도 이유였습니다. QLoRA는 2026년 7월에 EXAONE 3.5 7.8B에 맞춘 학습 호환 패치를 만들어 학습이 실행되는 것까지 확인했습니다. 4비트로 양자화하고 배치 크기를 1로 두었는데도 GPU 메모리 사용량이 8GB 중 7.69GiB였습니다. 8월 라이선스 확인에서 EXAONE이 연구 전용이고 파인튜닝한 모델도 같은 제약을 받는다는 것을 알았습니다. 곧 바꿀 모델에 학습을 투자할 이유가 없었고, 서비스와 학습이 같은 GPU를 써서 학습하는 동안 서비스가 멈추는 문제도 있었습니다. 9월에 Gemma 4로 교체하면서 학습 환경은 지웠습니다. 대신 8GB로 충분하고 서비스를 멈추지 않는 작은 분류 모델 학습을 했습니다. 실사용 질문이 수천 건 쌓이고 여러 단계 추론 질문이 10개 중 3개를 넘으면 다시 판정합니다.

## [03] AWS를 쓴 범위: EC2 시험 배포와 S3 이미지 저장

2026년 7월 28일에 서버를 이미지로 만들어 AWS EC2에서도 돌아가는지 확인했습니다. 이 EC2는 CPU 2개에 메모리 7.6GB이고 GPU가 없어서 백엔드와 Redis만 올렸습니다. 데이터베이스와 AI 모델(Ollama)은 자체 서버에 그대로 두고, EC2에서는 리버스 SSH 터널로 연결해 썼습니다. 터널용 키는 포워딩만 할 수 있게 제한했습니다. 데이터베이스 구조를 바꾸는 마이그레이션은 EC2에서 실행하지 않게 뺐습니다. EC2가 실제 데이터베이스에 연결되어 있어, 거기서 실행하면 실제 데이터의 구조가 바뀌기 때문입니다. 상태 확인 주소가 정상 응답을 주고 상권 1,650건이 조회되는 것까지 확인한 뒤 내렸습니다. 무료 구간이 아니어서 AWS에 계속 올려 두면 비용이 나가고, 데이터와 AI를 모두 자체 서버에서 끌어와 하는 일도 겹쳤기 때문입니다. 그래서 교육 과정에 다니는 동안은 학원 컴퓨터를 자체 서버로 만들어 운영하고, 과정이 끝나면 AWS로 다시 올릴지 검토하기로 했습니다. 외부 공개는 EC2 시험 전부터 Cloudflare Tunnel이 맡고 있었고, k3s로 옮긴 것은 그 뒤인 9월 7일입니다. AWS의 S3는 이미지 저장용으로 연결했습니다. 이미지 분석 결과와 관리자 화면에서 올린 이미지를 S3에 저장하고, 관리자 화면에서 올린 이미지에는 15분 동안만 열리는 주소를 만들어 돌려주게 했습니다.

## [05] k3s로 옮기면서 겪은 문제

k3s로 옮길 때 서비스가 끊긴 시간은 45초였고, 그 뒤 도메인 4개가 정상인 것을 확인했습니다. 옮기는 과정과 그 뒤에 세 가지 문제가 나왔습니다. 첫째, 호스트 포트를 직접 쓰는 파드는 새 파드가 포트를 잡지 못해 교체가 멈췄습니다. 개발 환경에서 먼저 발견해, 기존 파드를 먼저 내리고 새 파드를 올리는 방식(Recreate)으로 바꿨습니다. 둘째, 자체 서버를 켠 직후에는 도커에 남긴 그래프 DB와 자동화 도구가 준비되기 전에 정기 작업이 먼저 돌아 실패했습니다. 실패하면 두 번까지 다시 시도하게 했습니다. 셋째, 폴더를 읽기 전용으로 붙여 둔 탓에 분기별 수집 작업이 파일을 쓰지 못해 실패해, 쓰기 가능하게 바꿨습니다. 배포는 명령 하나로 합니다. 스크립트가 코드를 받고, 이미지를 만들며 커밋 번호를 기록하고, k3s에 넣어 적용한 뒤 다시 시작합니다. 화면은 main 브랜치에 올리면 Vercel이 자동으로 배포합니다.

## [05] 감시와 백업을 만든 과정

운영하면서 고장을 늦게 알아챈 일이 있었습니다. 자체 서버가 꺼져 데이터 수집이 멈춘 일과, 예전 이미지가 계속 돌고 있는데 상태 확인 주소는 정상이라고 답한 일입니다. 두 번 모두 고장을 알려 줄 감시가 없었던 것이 원인이었습니다. 그래서 수집한 자료가 얼마나 최신인지 감시하고, 상태 확인 주소에 지금 배포된 커밋 번호를 함께 보여 주게 했습니다. 백엔드를 일부러 내려 보니 2분 28초 뒤에 텔레그램 알림이 왔습니다. 데이터베이스는 매일 새벽 4시에 백업해 7일치를 보관하고, 8월 24일에는 백업을 임시 데이터베이스에 실제로 복원해 행 수가 맞는지 확인했습니다.

## [04] 테스트를 쓰는 방식

테스트는 pytest로 씁니다. 유스케이스는 목(mock) 라이브러리보다, 포트를 구현한 가짜 객체(스텁)를 넣어 검증하는 쪽을 우선합니다. 실제 AI 모델이나 외부 API를 부르는 테스트는 표시를 따로 달아, 평소 실행에서는 빼고 필요할 때만 돌립니다. 구조 규칙 위반은 테스트가 아니라 import-linter가 잡으므로, 구조를 건드린 변경은 둘 다 돌립니다. 가장 최근에 기록한 전체 통과 수는 1,193개(2026년 9월 16일)입니다. 로그인 토큰을 변조하거나 서명 방식을 없앤 토큰을 보내는 공격도 테스트로 막았습니다.

## [06] 수치로 확인한 개선

서울 평균을 매번 다시 계산하던 것을 한 번 계산해 저장해 두게 바꾸자, 상권 점수 조회가 첫 호출 330ms에서 저장된 값을 쓸 때 12.4ms로 줄었습니다. 답변을 쓰는 AI 모델을 고르는 1차 실측에서는 상권 답변 시간의 중앙값이 기존 모델 15.3초, 새 모델 8.1초였습니다(134문항 기준). 이유를 대지 않고 상권을 추천하는 답변은 33%에서 0%가 됐습니다. 답변이 오래 걸리는 질문이 있어, 기다리는 동안 지금 어느 단계인지 화면에 보여 주게 했습니다.
