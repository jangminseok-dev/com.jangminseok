## [04] 개발 방식과 본인이 맡은 범위

차곡노트는 장민석 혼자 만든 프로젝트입니다. 저장소의 커밋 412개는 모두 장민석 한 사람의 이름으로 기록되어 있고, 첫 커밋(2026-09-20)부터 가장 최근 커밋(2026-10-04)까지 15일이 걸렸습니다. 개발은 AI 코딩 어시스턴트와 함께 했습니다. 백엔드(FastAPI), 매장용 Flutter 앱, 보호자용 Next.js 웹, Docker Compose 개발 환경을 모두 직접 설계하고 구현했습니다.

작업은 서브 프로젝트 단위(기반, 고객과 반려동물, 방문과 예약, 기록과 미디어, 알림장)로 나눴습니다. 서브 프로젝트마다 설계 문서를 먼저 쓰고, 그다음 작업 단위로 쪼갠 구현 계획을 썼습니다. 네 번째 계획인 매장 앱 계획(2026-09-22)부터는 계획의 코드를 참조 구현에서 먼저 돌려 테스트가 통과하는지와, 일부러 코드를 망가뜨렸을 때 테스트가 실패하는지(변이 확인)를 본 뒤에 본 브랜치로 옮겼습니다. 참조 구현은 `ref/` 로 시작하는 참조 브랜치에 두었고(매장 앱 계획만 저장소 밖 참조 프로젝트), 옮긴 뒤에는 참조 브랜치와 차이가 없는지 대조했습니다. 설계와 다르게 간 것, 막지 않기로 한 동작, 미룬 것은 결정 기록(`_docs/decisions/`)에 서브 프로젝트마다 남겼습니다.

## [03] 구조 계약 6종과 허브 포트 조립

백엔드는 앱마다 adapter, app, domain 세 계층을 두고, 앱 사이는 허브(포트와 DTO만 가진 모듈)와 스포크(auth, tenancy, customer, visit, media 등)로 나눴습니다. 이 규칙은 import-linter 계약으로 검사합니다. 계층 방향, 스포크 상호 독립, app과 domain의 프레임워크 격리(fastapi, sqlalchemy 등 금지), 도메인 순수성(pydantic 금지), 허브 격리, core 격리 여섯 가지입니다. 설계 문서에는 다섯 가지였는데, 최종 검토 뒤 "core는 스포크를 import하지 않는다"를 계약으로 하나 더했습니다.

어려웠던 것은 스포크끼리 서로의 기능이 필요할 때였습니다. 예컨대 auth의 내 정보 조회에는 tenancy의 소속 목록이 필요합니다. 세 안을 검토했습니다. 허브에 레지스트리를 두는 안은 허브가 상태를 갖게 되고 요청 단위 DB 세션을 넘길 방법을 따로 만들어야 해서 버렸습니다. 조립 모듈을 계약의 예외로 두는 안은 결합이 예외 뒤로 숨어서 버렸습니다. 최종안은 소비하는 쪽에 호출되면 오류를 던지는 빈 "자리" 함수를 두고, 모든 스포크를 이미 import하는 진입점(main.py)이 FastAPI의 dependency_overrides로 구현을 꽂는 방식입니다. 같은 요청의 DB 세션을 공유하므로 스포크를 넘는 작업도 한 트랜잭션으로 묶입니다.

## [05] 멀티테넌시에서 겪은 문제와 고친 방법

토큰(RS256 JWT, 15분)에는 사용자 ID만 넣고 역할과 권한은 넣지 않았습니다. 사장이 직원을 내보내면 다음 요청부터 바로 403이 나야 하는데, 토큰에 역할을 담으면 만료될 때까지 옛 권한이 살아 있기 때문입니다. 대신 매장 범위 요청마다 소속, 권한, 매장 상태를 DB에서 다시 읽습니다. 캐시는 넣지 않았고, 그 부하는 운영 전에 다시 볼 과제로 남겼습니다(측정 전).

브랜치 최종 검토에서 중요한 결함 셋을 찾아 고쳤습니다. 첫째, 사장이 한 명도 없는 매장이 실제로 만들어지는 경합이 있었습니다. 대상을 읽은 뒤에 잠금을 걸어 그 사이 다른 요청이 역할을 바꾸면 낡은 값으로 판단했습니다. 멤버십을 바꾸는 모든 유스케이스가 맨 앞에서 매장 행을 잠그도록 바꿔 매장 단위로 직렬화했습니다. 둘째, 운영자 권한 확인이 "인터랙터 첫 줄을 빠뜨리면 열리는" 구조여서 라우터 가드로 옮겼습니다. 기존 설계 규칙을 뒤집은 결정입니다. 셋째, 가드가 붙어야 할 경로를 손으로 관리하던 목록은 새 경로를 빠뜨려도 테스트가 통과했습니다. 그래서 두 프로세스의 라우트 의존성 트리를 직접 훑어 빈 자리, 매장 확인이 없는 매장 경로, 운영자 가드가 없는 운영 경로를 찾는 구조 테스트로 바꿨습니다.

## [05] 알림장 토큰의 구조와 공개 조회 방어

토큰은 무작위 16바이트 공개 ID에 HMAC-SHA256 서명 앞 16바이트를 붙여 base64url로 인코딩한 43글자입니다. DB에는 공개 ID만 저장하고 토큰은 요청 때마다 다시 계산합니다. 그래서 살아 있는 링크를 다시 공유할 때 같은 주소를 줄 수 있고, DB만 유출되어서는 링크를 만들 수 없습니다. 서명이 틀린 토큰은 DB를 읽기 전에 떨어집니다. 토큰은 URL 경로가 아니라 `X-Report-Token` 헤더로만 받습니다. 경로에 두면 백엔드와 게이트웨이의 접속 기록에 그대로 남기 때문입니다.

횟수 제한은 처음 계획서에서 "10분에 실패 20회면 차단"을 그 주소의 모든 요청에 걸었습니다. 작업 검토에서 "한 통신망을 나눠 쓰는 보호자 전체를 익명 요청 20번으로 막을 수 있다"는 지적이 나와, 서명이 틀린 요청에만 걸도록 고쳤습니다. 추측 공격을 실제로 막는 것은 토큰의 크기이고, 실패 수 차단은 억지력이라고 정리했습니다. Redis가 장애일 때는 제한을 통과시키고 경고 로그만 남깁니다. 공개 응답은 칸을 하나씩 명시해 만들어 내부 메모가 섞이지 않게 했습니다. 링크를 끊어도 미리 복사해 둔 미디어 주소는 최대 48시간 열리고, 카카오톡 미리보기 카드는 카카오 서버에 남는 등 막지 못하는 다섯 가지는 결정 기록에 감수 항목으로 적었습니다.

## [05] 보호자 웹의 검증 방법

보호자 웹은 Next.js 서버가 백엔드 공개 API를 부르고, 보호자의 브라우저는 백엔드를 직접 부르지 않습니다. 토큰 형식(43글자)은 웹이 먼저 확인해 형식이 틀리면 백엔드를 부르지 않고 404를 냅니다. 원래 설계는 닫힌 링크에 410을 내려 했지만, 확인해 보니 App Router 페이지는 410, 429, 503을 낼 수 없어 상태 코드를 200과 404로 줄이고 화면 문구로 구분했습니다.

검증은 세 층으로 했습니다. Vitest 컴포넌트와 단위 테스트 125개, 빌드한 서버에 가짜 백엔드를 붙여 응답과 헤더, 로그에 토큰이 남지 않는지 보는 서버 응답 검사 46줄, 실제 브라우저(Playwright) e2e 11개가 모두 통과했고 e2e는 6.6초가 걸렸습니다. 테스트가 정말 결함을 잡는지는 변이로 확인했습니다. 열람 신호 컴포넌트를 빼거나, 뒤로 가기 처리를 빼거나, 긴 글 줄바꿈 규칙을 빼면 해당 테스트가 실패하는 것을 봤습니다. 이 결과는 개발 서버 위 chromium 기준이고, 실제 휴대폰 브라우저 확인은 운영 배포 뒤로 남겼습니다.

## [05] 미디어 업로드의 설계와 측정의 한계

사진은 앱이 원본(긴 변 3000px), 표시용(1080px), 썸네일(400px) 세 가지를 만들고, 원본을 만들 때 GPS를 포함한 EXIF를 지웁니다. 서버는 이미지를 디코딩하지 않기 때문에 개인정보 제거를 앱이 책임지는 구조이고, 서버 측 EXIF 검증은 공개 전 과제로 미뤘습니다. 업로드 출입증(presigned PUT)은 15분 유효합니다. 앱이 꺼지거나 인터넷이 끊겨도 기기에 저장한 대기열에서 남은 단계부터 이어 가고, 출입증이 만료되면 발급부터 다시 합니다. 로컬 파일을 원본으로 보기 때문입니다.

미디어를 방문 모듈 안이 아니라 별도 media 스포크로 뺀 이유는 방문 기록, 반려동물 프로필 사진, 알림장이 같은 자원을 함께 쓰기 때문입니다. 저장소는 포트 뒤에 두어, 개발에 쓴 MinIO를 운영에서 S3로 설정만 바꿔 옮길 수 있게 만들었습니다.

슬라이드의 12~115ms는 성능 벤치마크가 아닙니다. 영상 압축 진행률을 0.2초 간격으로 읽는 방식이 짧은 영상에서는 한 번도 값을 읽지 못하는 문제를 고치면서, iOS 시뮬레이터와 안드로이드 에뮬레이터에서 짧은 표본 영상의 압축이 그 시간에 끝난 것을 관찰한 값입니다. 그래서 시작과 끝에 진행률을 한 번씩 더 보내도록 고쳤습니다. 실기기에서 4K나 긴 영상의 압축 시간, 셀룰러에서 200MB 단일 업로드의 실패율은 아직 측정 전입니다.

## [05] 고객 검색의 규칙과 정합성 유지

검색어는 서버가 먼저 분류합니다. 숫자만 있고 4자리 이하면 전화 뒷자리가 그 숫자로 시작하는 고객을, 5자리 이상이면 전체 번호 부분 일치를, 한글 초성만 있으면 초성 검색을, 그 밖에는 이름 부분 일치를 찾습니다. 공백으로 나눈 여러 낱말은 모두 맞아야 합니다. 설계에서는 4자리 이하일 때 뒷자리 일치를 앞세우고 다른 결과와 섞어 보여 주려 했지만, 순위를 섞으면 커서 페이지와 충돌해서 "뒷자리로만"으로 좁혔습니다. 동작을 예측할 수 있게 하려는 선택입니다.

검색 줄은 고객, 반려동물, 질병을 바꾸는 모든 유스케이스가 같은 트랜잭션 안에서 다시 만듭니다. 이 재생성 메서드는 설계에서 리포지토리에 두려 했지만, 전용 검색 엔진으로 바꿀 때 색인 쓰기도 함께 바뀌어야 해서 검색 포트로 옮겼습니다. 고객 익명화와 반려동물 추가가 동시에 일어나면 익명화된 고객의 검색 줄이 되살아나는 경합을 찾아, 가족을 바꾸는 경로가 맨 앞에서 고객 행을 잠그게 했습니다. 전화번호 검색어가 서버 접근 로그에 남지 않도록 쿼리 문자열을 가리는 로그 필터도 달았습니다. 검색 속도는 아직 측정 전입니다.

## [04] 테스트를 쓰는 방식

계획서는 작업마다 테스트를 먼저 쓰고, 실패하는 것을 확인한 뒤 구현하는 순서로 적었습니다. 유스케이스 테스트는 목(mock) 라이브러리 대신 포트를 상속한 가짜 객체(스텁)를 씁니다. 포트에 메서드를 더하고 스텁에 빠뜨리면 객체를 만드는 순간 실패하므로, 빠뜨린 것을 바로 압니다. 통합 테스트는 별도 데이터베이스에 마이그레이션을 실제로 돌리고, 실제 PostgreSQL과 Redis, 파일 저장소에 붙어서 실행합니다. 마이그레이션과 코드의 테이블 정의가 어긋나면 실패하는 테스트도 두었습니다. 새 모듈을 만들 때 첫 통합 테스트는 "A 매장 멤버가 B 매장 주소를 부르면 403을 받는다"입니다.

## [05] 잠금 코드를 지워도 통과하던 동시성 테스트

동시에 들어온 두 요청이 서로 덮어쓰지 않는지 보려고, HTTP 요청 두 개를 한꺼번에 보내는 테스트를 썼습니다. 그런데 잠금 코드를 지워도 이 테스트가 5번 연속 통과했습니다. 로컬 데이터베이스는 요청 하나가 1ms도 안 되어 끝나서, 두 요청이 실제로 겹치는 순간이 우연히 만들어지지 않았기 때문입니다. 다른 동시성 테스트에서는 데이터베이스가 외래 키를 확인하면서 거는 잠금이 두 요청을 줄 세워, 잠금 코드가 없어도 통과했습니다. 테스트가 통과한다는 사실이 잠금이 동작한다는 증거가 아니었습니다. 그래서 데이터베이스 세션 두 개를 직접 열어 잠금이 걸리는 시점을 테스트가 정하게 바꿨습니다. 그리고 동시성 테스트는 잠금 코드를 빼면 실패하는지 반드시 확인한다는 규칙을 작업 규칙 문서에 넣었습니다.

## [06] 계획 단계에 악의적 시나리오 표를 두게 된 이유

AI 코딩 도구가 쓴 코드를 작업마다 검토했는데, 초기에는 검토 기준이 "계획서와 일치하는가"였습니다. 그래서 계획서 자체에 있던 보안 구멍 두 개는 작업별 검토에서 걸리지 않았고, 브랜치 전체를 보는 최종 검토에서 찾아 고쳤습니다. 그 뒤로는 계획을 세울 때 "악의적인 사용자가 이렇게 하면 어떻게 되는가"를 적은 표를 먼저 만들고, 검토도 그 표를 기준으로 합니다. 다음 계획에서는 작업 13개 가운데 11개에서 계획서 코드의 결함을 작업별 검토에서 잡았습니다. 미리 돌려 본 구현도 범위 끝 값을 넣으면 500 오류가 나는 문제는 잡지 못해서, 표에 범위 끝 입력을 더했습니다.

## [05] 훔친 토큰 하나로 계정을 빼앗을 수 있던 문제

계정 연결과 탈퇴 기능을 만든 뒤, 출시 전에 반드시 막아야 하는 문제를 결정 기록에 남겼습니다. 15분 동안 유효한 로그인 토큰 하나를 훔치면, 공격자가 자기 로그인 수단을 계정에 붙이고 원래 주인의 로그인 수단을 떼어 계정을 완전히 가져갈 수 있었습니다. 그래서 로그인 수단을 붙이거나 떼는 일과 탈퇴는 로그인한 지 300초 안의 토큰만 받게 했습니다. 로그인과 수단 해제가 동시에 일어나면, 해제된 수단이 30일짜리 세션을 쥐게 되는 문제는 브랜치 전체 최종 검토에서 찾아 고쳤습니다. 한 번 쓴 갱신 토큰이 다시 들어오면 도난으로 보고 모든 세션을 끊습니다. 네트워크가 불안할 때를 봐주는 유예 시간을 두는 방법도 있었지만 보안을 우선해 두지 않았고, 대신 앱이 갱신 요청을 한 번에 하나만 보내고 자동으로 다시 보내지 않게 했습니다.

## [03] 배포 상태: 개발 환경까지 만들었습니다

운영 서버에 배포한 적은 없고, 개발 환경까지 만들었습니다. Docker Compose로 서비스 7개(PostgreSQL, Redis, 파일 저장소 MinIO, API 서버, 로그인 서버, 게이트웨이 Caddy, 보호자 웹)를 띄우고, 포트는 모두 개발용 컴퓨터 안에서만 열리게 했습니다. 클라우드를 어디로 할지는 실제로 쓸 때 정하기로 미뤘습니다. 파일 저장은 S3와 같은 방식의 MinIO로 개발했고, 실제 AWS S3에서는 아직 확인하지 않았습니다. 운영으로 넘어갈 때 할 일(로그인 서버 개인키의 파일 분리, 의존성 버전 고정, 로그인 주소의 요청 수 제한 등)은 결정 기록에 모아 두었습니다.
